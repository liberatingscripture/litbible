# scripts/reconcile/ — Word master reconciliation tooling

**One-off tooling for a single reconciliation effort. Not part of `npm run
build`, `npm test`, or CI, and not referenced from the root `package.json`.**
It exists to bring `src/data/chapters/` back in line with the author's Word
master documents (see the approved plan this was built from), the same way
`scripts/build-alignment.mjs` and `scripts/build-favicons.mjs` are
committed-output, run-by-hand tooling outside the normal build pipeline —
except everything under `scripts/reconcile/` is source code and tests
(committed), while its `out/` directory is scratch output regenerated by
running the tools (see "Outputs" below).

**Never point any tool here at chapter JSON with intent to write it without
a human decision in between.** `lib/json-splice.mjs` is explicit about this
in its own header: it never reformats a whole file (`JSON.parse` ->
`JSON.stringify` would move all 260 files' manifest hashes for zero content
change — see CLAUDE.md's Build Pipeline step 5 and the glossary-feed silent-
failure precedent it documents), and every write path in this tooling is
designed to fail loudly rather than guess.

## What each phase does

The approved plan splits this into four phases. **Only Phases 1, 3, and 4's
*libraries* are built and tested here; Phase 2's ledger generator is written
but has never been run, and there is no `apply.mjs` yet** (Phase 3's actual
file-writing step). Building `apply.mjs` and running `build-ledger.mjs` for
real are future work, gated on a human reviewing the ledger this generates.

| Phase | What | Entry point | Status |
|---|---|---|---|
| 1 | Master re-extraction (run-aware XML tokenizer, dual verse-marker cross-check) + the comparison gate | `lib/docx-runs.mjs`, `lib/docx-verses.mjs`, `gate-report.mjs` | Built, tested, gate run (see `out/GATE.md`) |
| 2 | Ledger: classify every master/repo difference into buckets A-E | `build-ledger.mjs` | **Written, never run** — see warning below |
| 3 | Apply: byte-safe splicing of approved patches into chapter JSON | `lib/json-splice.mjs` | Library built and tested; no `apply.mjs` driver exists yet |
| 4 | Quote normalization for restored master text | `lib/curl-quotes.mjs` | Built and tested |

## Source data (never committed)

- **Master XML** — the Word masters unpacked to `word/document.xml` +
  `word/footnotes.xml` per book, 26 books, ~17MB. This lives outside the repo
  entirely (a session scratchpad or wherever you unpack the `.docx` files
  next). Point every tool at it via `--master-dir=<path>` or the
  `MASTER_XML_DIR` environment variable — there is no committed default that
  works outside the session that built this tooling.
- **v1 audit artifacts** (`gate-report.mjs` only) — the prior audit's
  `results.json` and its own `docx-xml.mjs` extractor, read-only, so the
  Phase 1 gate can diff v2's output against v1's and (for the footnote-text-
  match assertion) recompute v1's full extraction rather than trusting the
  truncated subset `results.json` recorded. Point at these via
  `--v1-results=`/`V1_RESULTS_JSON` and `--v1-docx-xml=`/`V1_DOCX_XML_MODULE`.
  Only needed to re-run the Phase 1 gate itself, not for Phase 2/3/4 tools.

None of this is fetched or cloned automatically (unlike the alignment
tooling's MorphGNT clone, which at least has a documented `git clone`
command) — the master `.docx` files are the author's own working documents,
not a public corpus.

## Running each piece

```bash
# Phase 1 gate — re-extracts every master book with the run-aware v2
# extractor, diffs the resulting findings against v1's results.json, and
# writes evidence (never a verdict) to out/GATE.md + stdout.
node scripts/reconcile/gate-report.mjs \
  --master-dir=<path to unpacked master XML> \
  --v1-results=<path to v1 results.json> \
  --v1-docx-xml=<path to v1's docx-xml.mjs>

# Phase 2 ledger — DO NOT RUN without a reviewer ready to read out/INDEX.md
# and the per-book Markdown files it produces. See the warning below.
node scripts/reconcile/build-ledger.mjs --master-dir=<path> [--out-dir=<path>]

# Tests (json-splice.mjs and curl-quotes.mjs - see "Tests" below)
node --test "scripts/reconcile/test/*.test.mjs"
```

Every entry point resolves its master-dir/output-dir the same way: a
`--flag=value` CLI argument first, then an environment variable, then (for
`gate-report.mjs` only) a hardcoded session default that will not exist on a
different machine. Passing `--master-dir` explicitly is always safe.

### `build-ledger.mjs` — WRITTEN, NOT RUN

This script has never been executed against real data. It was written to
fully implement the plan's Phase 2 classification pipeline (existence check
→ cosmetic gate → git settle-window → word-level LCS shape → bucket, with a
hand-review override for patch warnings/structured HTML/bracketed chapters —
see its own header for the exact algorithm), and its supporting libraries
(`lib/word-diff.mjs`, `lib/git-settle.mjs`, `lib/verse-span.mjs`) were each
smoke-tested against real corpus data and real git history *in isolation*,
but the full orchestrator was not run end-to-end. Before trusting its
output:

- **Re-check the bucket-A subclass thresholds in `lib/word-diff.mjs`.** They
  are principled defaults reasoned from the plan's description (e.g. "no
  added/removed words, only punctuation/case differences" for the 227
  trailing-period defect), not calibrated against the real ~962 footnote /
  ~263 scripture findings this reconciliation is scoped to. A first run's
  bucket-A subclass counts should be compared against the plan's cited
  figures (11 placeholder / 52+13 truncated-or-summarized / 287+227+66
  punctuation-or-case / 470+139 rewritten) before relying on the split.
- **`out/decisions.json`** (the sidecar of owner approvals `apply.mjs` will
  eventually read) has an assumed shape —
  `{ [recordId]: { decision: "approved"|"rejected"|"deferred", note?: string } }`
  — documented in `build-ledger.mjs`'s own comments, since the plan doesn't
  fully specify it. Confirm this shape matches whatever a human reviewer
  actually produces before a future `apply.mjs` depends on it.
- **Verse patches only cover the common case.** `lib/verse-span.mjs` locates
  a verse's span within its containing `paragraphs[i]` string, and
  `build-ledger.mjs` reconstructs the `<span class="vglue">` marker wrapper
  around the restored text's own first word (verified against real corpus
  examples — see the module's own comments). A verse that spans a paragraph
  break with no marker of its own (a continuation, per CLAUDE.md's Chapter
  JSON Format section) or whose restored text begins inside a formatting
  tag is deliberately left `patch.newValue: null` with a `forceHandReview`
  reason — not guessed at.
- **`apply.mjs` does not exist.** Phase 2 ends at the ledger for a reason:
  the plan calls this "stop here for review." Writing the file-mutation
  driver that reads `out/ledger.json` + `out/decisions.json` and calls
  `lib/json-splice.mjs` per approved record is future work for a session
  *after* a human has read the ledger this produces.

## Outputs (`out/` — gitignored; everything else under `scripts/reconcile/` is committed)

- `out/results-v2.json`, `out/GATE.md` — Phase 1 gate output (already
  generated once this session; see `out/GATE.md` for its findings).
- `out/ledger.json`, `out/books/<bookKey>.md`, `out/INDEX.md`,
  `out/deferred-master-only.json` — what `build-ledger.mjs` *would* write
  if run. One Markdown file per book rather than a single report, per the
  plan (a 921KB single-file report was judged unreviewable). `INDEX.md` is
  a per-book × per-bucket count table. `deferred-master-only.json` lists
  footnotes/verses the master has that the repo doesn't at all — out of this
  reconciliation's bucket A-E scope entirely; see the plan's "Deferred" list
  in its follow-up-document section.
- `out/decisions.json` — NOT generated by any tool here; a human-authored
  sidecar `build-ledger.mjs` reads back in on a later run so `ledger.json`
  stays regenerable without losing approval state.

## Tests

```bash
node --test "scripts/reconcile/test/*.test.mjs"
```

**Use the glob form above, not a bare directory.** `node --test
scripts/reconcile/test/` (or `test` with no trailing slash) does not recurse
into the directory in this environment — the same behavior the root
`package.json` already routes around (`"test": "node --test
\"test/**/*.js\""` is a glob for exactly this reason, confirmed by the same
failure against the repo's own pre-existing `test/` directory, not something
specific to this tooling). Node builtins only, no dependencies — these tests
run even in a worktree with no `node_modules` installed.

Coverage is deliberately weighted toward `json-splice.mjs` (the safety-
critical module) and `curl-quotes.mjs` (the one that has to get real corpus
edge cases right — see its header on the apostrophe/quote ambiguity and the
independent double/single toggle correction, both found by testing against
real chapter text during development, not assumed up front). The other
`lib/` modules were smoke-tested against real corpus data and real git
history during development (not committed as throwaway scripts) but do not
have formal `node:test` coverage — reasonable follow-up if `build-ledger.mjs`
is ever run for real and its output needs debugging.

## The review tool (`npm run review:reconcile`)

Serves a localhost-only UI on port 4600 (`--port` to change; `--buckets=B,C,D`
to scope it) and writes decisions straight into `out/decisions.json` as you make
them — no save step, so a crash costs at most one span.

**It asks per hunk, not per record.** Buckets B and C were dated per footnote and
per verse, which is too coarse: a note edited in August carries whatever import
damage it still had into bucket B alongside the edit, so one record routinely
holds both. `1corinthians-10-fn-g` has stripped macrons (the master is right)
and "reflects" → "highlights" (the repo is right) in the same footnote. Asking
"master or repo?" about that record has no correct answer. Asking it about each
span does.

Each span is one of three kinds, and only the third needs a person:

| kind | what differs | default |
|---|---|---|
| `mechanical` | no word at all — diacritics, quote characters, spacing | take the **master**; these are the import's known damage classes |
| `structural` | markup only, same visible words | keep the **repo** — its markup is authored and the Word master has none |
| `judgment` | the words | nothing; this is the question |

The structural default direction is load-bearing. `1corinthians-11-fn-b` builds
its chiasm out of `<span class="chiasm-key">` / `<span class="chiasm-text">`, and
taking the master there would delete the whole structure while changing not one
word.

Judgment runs both ways, which is why it cannot be automated: the repo has a
typo in `1corinthians-10-fn-ee` (`arazeloo` for `parazeloo`) and the master has
one in `1corinthians-2-fn-q` (`Life-breah` for `Life-breath`).

**Runs of spans are classified too, not just single spans.** Word keeps its own
run boundaries, and they rarely match a word: `soter` arrives as five separate
`<em>` pairs, one per letter, and `hesed</em>,` as `hesed,</em>`. Rebuilding a
verse moves its first word inside the `vglue` span, which five verses in the
corpus close before the word instead. Each of those produces a cluster of spans
that individually look like wording changes and together change no letter. So
consecutive `judgment` spans are re-checked as a group, shortest group first,
and a group whose two sides carry identical visible text takes the kind the
concatenation earns. That retired 70 of 366 false questions. Two guards keep it
honest: only `judgment` spans are eligible, so a macron fix beside a markup move
keeps its own default; and the sides are concatenated **in order** with the
untouched text between them included, so a genuine transposition does not
cancel. It leaves real finds standing — `matthew-21-fn-l` spells the same Greek
word `hypsistois` once and `hupsistos` four times, and that stayed a question.

**Records that are wholesale rewrites open as a whole-version comparison.**
Per-span is the right question for a note with three spot edits and the wrong
one for `matthew-12-fn-z`, which differs in 51 places across 92% of its text:
rendered span by span it is a wall of choosers and neither version can be read
as a sentence. Five records hold 129 of the 296 questions this way, so they open
as two readings side by side with one button each, and a toggle down to spans
for anyone who wants to mix. Taking a version sets only the `judgment` spans —
`structural` ones keep their own default, so choosing the master can never
delete authored markup.

Two structural rules it lives inside, the same two as `scripts/alignment-review/`:

1. **The UI is served from the Node process by exact-path allowlist**
   (`STATIC_FILES` in `review/server.mjs`), never from `public/` — Astro copies
   `public/` into `dist/` as a filesystem operation, so a `.gitignore` there
   stops a commit but not a deploy. `review-core.mjs` is one of the allowlisted
   paths because the browser imports the *real* module rather than a second copy
   of rules that have to agree with the server's.
2. **A decision records the SHA of the text it was made against.** `apply.mjs`
   writes the composed `resolvedValue` — master where you took it, repo where you
   kept it, which is neither side whole — and refuses it when `baseSha` no longer
   matches the record. Edit a chapter, regenerate the ledger, and any decision
   whose ground moved is re-asked rather than applied blind.

Apply what you have decided, at any point:

```bash
node scripts/reconcile/apply.mjs --decision=approved --write
```
